# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is
**E-Magang Kota Madiun** ("magange") — an internship-application portal for the Madiun city government. Three roles (app/Enums/UserRole.php): **Mahasiswa** (applicant), **Admin Verifikator** (screens incoming applications), **Admin OPD** (the placement agency that approves/rejects and manages active interns). UI, code comments, and domain terms are in **Indonesian** — match that language when editing.

The application lifecycle is the enum app/Enums/ApplicationStatus.php: pending_verifikator → forwarded_opd → **waiting_tte** → approved → ongoing → completion_submitted → **needs_certificate** → completed (with rejected as a terminal branch). The two bolded statuses are the **TTE (tanda tangan elektronik) batch** — see "Batch TTE" below; `completed` now means "period ended AND a signed certificate was issued", not just "period ended". InternshipApplication is the central model; supporting models cover OPDs, OPD signers + letter templates, OTP tokens, status-log audit trail, documents, final reports, satisfaction surveys, FAQs, and form rate-limiting.

## Stack
Laravel 13 (PHP 8.3+) + Inertia v3 + React 19 + TypeScript, built on the laravel/react-starter-kit. Vite for bundling, Tailwind v4 for styling, shadcn/ui ("new-york" style) for components, Pest v4 for tests, PostgreSQL for the database. Authentication is handled by Laravel Fortify, plus a custom email-OTP login flow for mahasiswa (WhatsApp numbers are collected as contact data only — OTP delivery is email, via SendOtpEmailJob).

Detailed framework conventions (PHP style, Inertia v3 patterns, Pint, Pest, Wayfinder, Boost MCP tooling) live in AGENTS.md — read it before non-trivial changes. Domain-specific skills (Inertia/React, Wayfinder, Fortify, Pest, Tailwind, Laravel best-practices) live in .cursor/skills/**; AGENTS.md requires activating the relevant skill when working in that domain. This file covers what's specific to *this* repo.

## Commands
- **composer dev** — the everyday runner: boots `php artisan serve`, `queue:listen --queue=emails,default`, and `npm run dev` (Vite) together via concurrently. The queue worker is part of this; without it, dispatched Jobs/Mail never process.
- **composer ci:check** — the full local gate, and a superset of CI: JS lint (eslint) + format check (prettier) + TS types (tsc) + `composer test`. `composer test` itself chains Pint `lint:check` + PHPStan `types:check` + `php artisan test`. Run this before calling a batch done.
- **php artisan test --filter=SubmissionServiceTest** — run one Pest test file/case (or `php artisan test tests/Unit/SubmissionServiceTest.php`).
- **composer lint** (Pint) / **npm run types:check** (tsc) / **npm run lint** (eslint --fix) / **npm run format** (prettier --write) — run individual gates while iterating. PHPStan (level 7, paths app/ bootstrap/app.php config/ database/ routes/) may need `--memory-limit=1G` locally (default 128M php.ini limit is too low).
- **npm run build** — production Vite build. Not needed for the test suite (tests/TestCase.php calls `withoutVite()`), but CI runs it, so a broken build fails CI even when tests pass.
- **php artisan wayfinder:generate --with-form** — regenerate the typed route helpers. `npm run dev` runs it first, so the frontend dev server needs artisan (and a reachable DB) to boot.
- **CI reality check.** Two workflows, not one: `.github/workflows/lint.yml` (Pint + prettier + eslint, PHP 8.4) and `tests.yml` (`composer types:check` + `npm run build` + `php artisan test` across a PHP 8.3/8.4/8.5 matrix). Both trigger **only on develop/main/master/workos** — feature branches like `front` get no CI, so `composer ci:check` locally is the only gate that actually runs.
- **php artisan schedule:test --name="magang:transition-statuses"** — dry-run the daily 01:00 status-transition cron (routes/console.php → app/Console/Commands/TransitionApplicationStatuses.php). PostgreSQL is the DB; a `.env` DB connection must be reachable for artisan/test.
- **php artisan migrate:fresh --seed** — DatabaseSeeder chains OpdSeeder → AdminSeeder → FaqSeeder → RegistrationSeeder in that dependency order (OPDs before admins, admins before FAQs). RegistrationSeeder injects a real-shaped pending application directly into the DB because the public form's reCAPTCHA can't be automated.

**Package manager.** Both `package-lock.json` and `pnpm-lock.yaml` are committed (there's a `pnpm-workspace.yaml` + `.npmrc` with `ignore-scripts=true`). `composer dev`/`composer ci:check` invoke the **npm** scripts, so npm is what the documented flows use — but the pnpm workspace config exists too. Pick one when installing and don't let the other lockfile drift.

## Business Logic & Strict Constraints (CRUCIAL REVISION)
When editing workflows, controllers, or UI, you MUST strictly adhere to the following business rules:

1. **Authentication Split & Security:**
   - **User (Mahasiswa):** Login without a password. Input Email -> receive OTP -> login. OTP expires after **5 minutes** (OtpService TTL_MINUTES).
   - **Admin (Verifikator & OPD):** Login using a conventional form (Username & Password) on a specific route `/admin/login`. DO NOT use OTP for admins.
   - **Single Session Limitation:** 1 Browser MUST NOT be able to log into 2 different accounts simultaneously. If detected, return `403 Forbidden`.
   - **Progressive OTP lockout (Fibonacci):** 3 wrong OTP entries → active tokens invalidated (user must resend) and resend is blocked for a cooldown that escalates per lockout level along the Fibonacci series (1, 1, 2, 3, 5, 8… minutes). Counter resets on successful login OR after 24h with no attempts. Implemented in app/Services/OtpLockoutService.php + otp_lockouts table, wired into Auth\OtpLoginController (both send and verify are blocked while locked; the page shows a live countdown via the `lockoutSeconds` flash prop).

2. **Role-Based Form & UI Constraints:**
   - **Public Form (Welcome Page):** `Jurusan` (optional) and `Keahlian` (textarea) fields sit right above the `alamat_lengkap` field — they map to the `major` / `skills` columns on internship_applications. The form also collects **required** WhatsApp numbers for the supervisor and guardian (`campus_supervisor_whatsapp` / `guardian_whatsapp` columns) — admin review panels display them.
   - **Admin Verifikator:** When reviewing applications, they MUST see the `Jurusan` and `Keahlian` data. They are ONLY allowed to fill in "Catatan Khusus Admin Verifikator". They CANNOT and DO NOT assign Divisi, Pembimbing Lapangan, or Penanggung Jawab.
   - **Verifikator manages OPDs:** full CRUD at verifikator/opd/* (Verifikator\OpdController, mirroring the FaqController pattern; deletion is refused while quota_used > 0, quota can't drop below quota_used). The older "Kelola Kuota OPD" page (verifikator/kuota) and PATCH kuota/{opd} are **kept for compatibility** — Admin OPD still edits its own quota through them.
   - **Admin OPD Dashboard:** The status filters MUST be ordered as: `Perlu Keputusan` (with yellow background), `Disetujui`, `Sedang Magang`, `Selesai Magang`, `Ditolak`, `Semua`. Since the 2026-07-30 redesign that order is satisfied across **two tiers** (read left→right, then top→bottom), not one row — `ACTION_FILTERS` renders Perlu Keputusan / Menunggu TTE / Perlu Sertifikat as "Butuh tindakan" cards, `STATUS_FILTERS` renders the rest as chips on the table toolbar. They are one control surface split by role; **don't merge them back into a single row and don't re-add a separate stat-card strip** — that duplication (cards and chips writing the same `filter` state with different membership) was the bug the redesign removed.
   - **Admin OPD Action:** When clicking "Putuskan" and selecting ACC (approve), Admin OPD is REQUIRED to fill in `Divisi/Bidang`, `Pembimbing Lapangan`, and `Penanggung Jawab`. Add an alert text below this form stating: *"Notif ini akan dikirim ke peserta magang. Peserta akan datang berkunjung ke kantor setelah diterima pengajuan ini"*.

3. **Status Automation (Cron Job):**
   - A daily scheduler runs at `01:00 AM` **WIB** to automatically update application statuses (routes/console.php → `magang:transition-statuses`). `config('app.timezone')` stays **UTC** (changing it would reinterpret every timestamp already in the DB), so the schedule pins its own zone via `config('app.schedule_timezone')` (env `APP_SCHEDULE_TIMEZONE`, default `Asia/Jakarta`). 01:00 WIB = 18:00 UTC the *previous* day — so the command must read "today" in that same zone (`Date::now(config('app.schedule_timezone'))`), otherwise every transition is a day late. Covered by tests/Feature/Feature/Penyelesaian/TransitionTimezoneTest.php.
   - If status is `approved` and `start_date` <= today, update to `ongoing` (Sedang Magang).
   - If status is `ongoing` and `end_date` <= today, update to `needs_certificate` (Perlu Sertifikat) — **`completed` only after the signed certificate is uploaded** (TTE batch). Applications without a signer snapshot keep the old direct-to-`completed` behaviour. (`<=`, not `==`, so a missed scheduler run still catches up.)
   - **Period rules.** `duration_months` is never trusted from the client — StoreApplicationRequest always recomputes it from the date range as `round(days / 30.4375)`, min 1. The range itself is capped at 12 months by `end_date` → `before_or_equal:{start + 1 year}` (rejected, not silently clamped); welcome.tsx mirrors that cap through the `DatePicker` `max` prop + `maxTanggalSelesai()`. `SubmissionService::resubmit()` shifts a past period forward to start today, preserving its length in days, and notes the shift in the status log.

4. **Completion Actors (4 Triggers for 'Completed'):**
   - The status change to `completed` can be triggered by 4 different actors: 1) System (via Cron Job), 2) User (uploading final report and checking the completion box), 3) Admin Verifikator (manual button), and 4) Admin OPD (manual button).
   - Upon completion, **Admin OPD** (since batch 5 — moved from Verifikator) reviews the final report and uploads the final certificate from the "Kelola Peserta" detail dialog. User MUST fill out a satisfaction survey before the certificate download button is unlocked.

5. **Email Notifications:**
   - Emails must have a large blue header text: "magang kota Madiun".
   - Approval emails must include applicant details, placement details (Divisi, Pembimbing, Penanggung Jawab), a PDF attachment, and a specific instruction: *"Anda diharapkan hadir di kantor OPD terkait dengan menemui perwakilan dari bidang [Nama Bidang]... dipandu oleh [Nama Pembimbing]"*.

## Batch TTE — surat penerimaan & sertifikat bertanda tangan (SELESAI 2026-07-30)

Approve OPD dengan penandatangan → `waiting_tte` (draft PDF dibuat, TANPA email); unggah surat bertanda tangan → `approved`/`ongoing` + SendSignedAcceptanceLetterJob. Daftar status sah sekarang dijaga cast enum di level aplikasi saja, jadi **status baru tak lagi butuh migration constraint** (dan pelajaran: `->change()` di SQLite membangun ulang tabel sehingga bug seperti ini lolos dari suite SQLite — jalankan suite di PostgreSQL).

## Architecture
**Inertia, not an API.** Controllers return Inertia::render('page-name', [...props]) (or Route::inertia() for prop-less pages). React page components live in resources/js/pages/ and receive those props directly. There is no REST/JSON API layer — server and client are coupled through Inertia.

**Layouts: starter-kit pages are global, role dashboards self-wrap.** resources/js/app.tsx's layout() callback maps by page name: auth/* → AuthLayout, settings/* → [AppLayout, SettingsLayout], everything else → AppLayout. **But** the role dashboards and branded public pages (mahasiswa/*, verifikator/*, opd/*, auth/otp-login, pengajuan/baru, lacak, bantuan, pengaturan, welcome) return null there and instead import and wrap **MagangLayout** (resources/js/layouts/magang-layout.tsx) themselves. So whether a page imports its own layout depends on which group it's in — check app.tsx first. MagangLayout is the branded (Pemkot Madiun blue #106feb) dashboard shell; it takes navItems and exports per-role nav arrays (mahasiswaNav, verifikatorNav, opdNav).

**Every self-wrapping MagangLayout page MUST receive a `user` prop** (`'user' => new MagangUserResource($request->user())`) — the shell reads `user.role`/`user.name` unconditionally and does **not** fall back to the `auth.user` shared prop. Forgetting it is a silent failure mode: the server still returns **200**, but React throws while rendering and unmounts the whole tree, so the page is a blank white screen with nothing in the Laravel log. That bit `/opd/surat` (fixed 2026-07-30); `tests/Feature/Feature/Opd/TteFlowTest.php` now asserts the prop on the TTE pages. When adding a page here, assert `has('user.name')` in its test.

**Shared props** (available to every page via usePage().props) are defined in app/Http/Middleware/HandleInertiaRequests.php: name, auth.user, recaptchaSiteKey, sidebarOpen, plus the flash props success / error / generatedCredentials.
**Routing & Wayfinder.** Routes are in routes/web.php and routes/settings.php. The @laravel/vite-plugin-wayfinder plugin generates typed TS helpers from those routes into resources/js/actions/ (controller actions) and resources/js/routes/ (named routes). **These directories are generated — never edit by hand.** Import route helpers from @/actions/... or @/routes/...; they regenerate on vite build/dev.

**Authentication via Fortify.** There are no hand-written login/register/password controllers — Fortify provides them, configured in app/Providers/FortifyServiceProvider.php. Custom user-creation and password-reset logic lives in app/Actions/Fortify/. Reusable validation rules are traits in app/Concerns/ (PasswordValidationRules, ProfileValidationRules). Beyond Settings/, first-party domain controllers now exist under app/Http/Controllers/{Auth,Mahasiswa,Opd,Verifikator}/ for the wired action routes; request validation lives in FormRequests under app/Http/Requests/ (mirroring the same role folders). Role-based route access uses the role: middleware alias → app/Http/Middleware/EnsureUserRole.php (registered in bootstrap/app.php), matching e.g. role:admin_opd or role:admin_opd,admin_verifikator against UserRole->value (403 on mismatch). **Admin login is served by Fortify itself, not a hand-written controller** — config/fortify.php sets `paths.login = 'admin/login'`, and FortifyServiceProvider wires `Fortify::loginView(auth/admin-login)` + `Fortify::authenticateUsing(...)` to match on `username` + password and restrict to admin roles (there is no AdminLoginController). This is separate from the mahasiswa OTP flow (Auth\OtpLoginController). The OTP login (auth/otp-login page, OtpToken model, FormRateLimit) is the project's own addition on top of Fortify; the User.password column stores the active OTP hash rather than a chosen password.

**Anti-abuse layer.** Both login paths apply the InvalidatesOtherSessions trait (app/Concerns/) — the mahasiswa Auth\OtpLoginController and the admin Fortify flow (wired in FortifyServiceProvider): on successful login it clears every other session for that user (database session driver), enforcing single-session-across-devices on top of the per-controller 403 guard. The public submission form is protected by Google reCAPTCHA **v3** (score-based) via the App\Rules\Recaptcha rule — required only when config('services.recaptcha.secret') is set, so tests/local dev without keys still pass; the same rule guards OTP send and admin login (actions 'daftar'/'otp_send'/'admin_login', frontend hook resources/js/hooks/use-recaptcha-v3.ts). Submission spam is additionally throttled by RateLimitService/FormRateLimit.

**Global middleware (bootstrap/app.php).** Three things are registered globally, not per-route, so they affect every request: `SanitizeInput` (appended to the global stack — runs *before* FormRequest validation), `EnsureMustChangePassword` (appended to the `web` group, after HandleInertiaRequests, plus aliased as `password.changed`), and `trustProxies(at: '*')` — the last one exists so ngrok/reverse-proxy `X-Forwarded-*` headers are honoured and assets/redirects don't downgrade to `http://`. Cookies `appearance` and `sidebar_state` are excluded from encryption.

**Frontend imports** use the @/ alias → resources/js/ (see tsconfig.json). Add new shadcn components with the shadcn CLI (config in components.json); they land in resources/js/components/ui/.

**Domain service layer.** Business logic lives in app/Services/, not controllers — when the HTTP layer is written, controllers should be thin and delegate here. The lifecycle state machine is SubmissionService (submit, forwardToOpd, approve, reject, startOngoing, complete): each transition runs inside a DB::transaction, calls guardStatus() to reject out-of-order moves (throws DomainException), writes an ApplicationStatusLog audit row, mutates side state (e.g. approve increments the OPD's quota_used), and dispatches a job. Match this shape for new transitions. Other services: CertificateService (upload to the **private** local disk, certificates start is_download_locked = true), OtpService (5-minute token TTL), OtpLockoutService (progressive Fibonacci lockout, see Business Logic above), ImageService (normalizes the registration pas foto via Intervention Image — scaleDown to 1000px + JPEG q80, falling back to storing the original when GD/Imagick is missing so registration never fails; local dev PHP may lack GD, production should have it), RateLimitService (anti-spam via FormRateLimit). Two services are bound by contract in app/Providers/AppServiceProvider.php (OtpServiceContract → OtpService, PengajuanServiceContract → SubmissionService) — type-hint the contract, not the class.

**Async side effects: Jobs + Mail + PDF.** Services dispatch queued app/Jobs/* (all on the emails queue, tries = 3 with backoff) for everything user-facing: confirmation, rejection, acceptance letter, certificate notice, OTP. Each job sends an app/Mail/* mailable rendered from resources/views/mail/*.blade.php. PDFs use **barryvdh/laravel-dompdf** — GenerateJobAcceptanceLetter renders resources/views/pdf/acceptance_letter.blade.php, stores it on the private local disk, and records the path on the application. The queue worker runs as part of composer dev; without it, dispatched jobs won't process.

**Private-disk file surfaces.** All user-uploaded files live on the **private** `local` disk (never public) and are served through auth-guarded controllers, never a direct URL — follow this pattern for any new upload. Path columns on internship_applications: `photo_path` (pas foto, served via GET pengajuan/{application}/foto → ApplicationPhotoController) plus the optional supporting documents `surat_pengantar_path` / `cv_path` / `portfolio_path` (uploaded "jika ada" from the welcome #daftar form; served inline via GET pengajuan/{application}/dokumen/{surat-pengantar|cv|portofolio} → ApplicationDocumentController; size caps: surat pengantar/CV 2MB, portofolio 10MB — keep the frontend "maksimal 2MB/10MB" messages in sync with StoreApplicationRequest). Both are authorized by InternshipApplicationPolicy::view (mahasiswa: own application only; Verifikator: all; OPD: only applications forwarded to its OPD). Users carry `avatar_path` — for mahasiswa it's auto-populated from the registration pas foto at account creation (no separate upload step) and served via GET profile/avatar → ProfileAvatarController (parameter-less, always the authed user, so it can't leak another user's photo). Certificates go through CertificateService onto the same private disk.

**Ticket numbers.** The canonical application ticket format is `MGG-YYYY-NNNNNN` (e.g. `MGG-2026-000042`), generated by SubmissionService::generateTicketNumber (`sprintf('MGG-%d-%06d', ...)`). The public lacak page and every mahasiswa/verifikator/opd page display/validate this format — keep frontend masks/regex in sync. An older `EMG-` prefix was retired; treat any surviving `EMG-` as suspect.

## Tests
Pest v4. Unit tests for services live in tests/Unit/ (SubmissionServiceTest, CertificateServiceTest, OtpServiceTest, OtpLockoutServiceTest, RateLimitServiceTest). Feature tests have a **doubly-nested** layout: newer role/flow coverage sits under tests/Feature/Feature/{Auth,Mahasiswa,Opd,Verifikator,Penyelesaian,Security}/ — put new controller/flow tests there to match. tests/Feature/Feature/Penyelesaian/EndToEndFlowTest.php walks the full lifecycle and is the best reference for wiring a new transition; Security/{SingleSessionTest,RecaptchaRateLimitTest} cover the anti-abuse guards. Local PHP may lack the GD extension, so tests that need an uploaded image use `UploadedFile::fake()->create(..., 'image/jpeg')` rather than `->image()` — follow that pattern.

tests/Feature/{Auth,Settings}/ (single-nested) are the **untouched starter-kit tests**; the doubly-nested tree is this project's own. **Expected baseline: ~202 tests, 10 skipped** — the skips are not a regression. Nine come from Fortify features this app deliberately leaves off (registration, password reset, two-factor), which bail out through `TestCase::skipUnlessFortifyHas()`; one is an explicit `->skip()` in Mahasiswa/ApplicationControllerTest for a page that was never built (the live registration form is welcome.tsx `#daftar`). A run that reports 0 skips means the suite changed, not that something got fixed.
