# Feature Prompt: Alur TTE (Surat Penerimaan & Sertifikat) — E-Magang Kota Madiun

## Context (read first)
Read the project's existing documentation, architecture notes, and any
session/handoff files in the repo before starting. This feature touches:
PDF generation, the peserta status machine, email triggers, the OPD data
model, letter/certificate templating, and the Admin OPD dashboard/sidebar.

## Background / Problem
Surat Penerimaan and Sertifikat PDFs are currently generated with a hardcoded
letterhead and signature for "Kepala Dinas Komunikasi dan Informatika" for
ALL OPDs, and are auto-emailed to peserta immediately — without ever being
physically/digitally signed by the actual authorized official. This is
factually wrong for every OPD except Diskominfo, and skips the real-world
signing step entirely.

## Goal
1. Make the letterhead and signature on both documents dynamic per OPD, with
   a reusable list of authorized signers per OPD.
2. Require Admin OPD to upload the actually-signed PDF before it's emailed
   to the peserta.
3. Apply the same signing mechanism to two documents — **Surat Penerimaan**
   (triggered on approval) and **Sertifikat** (triggered automatically when
   magang period ends) — with content and trigger differing per document.
4. Let Admin OPD manage the editable body text of both document templates.

---

## 1. "Kelola OPD" — Dashboard Card (NOT a sidebar menu)

Stays as a card on the Admin OPD **Dashboard** (do not create a separate
sidebar menu for this). Merge the existing "Kuota Magang OPD" and "Tag
Kompetensi" sections plus two new sections into one card titled
**"Kelola OPD"**:

**a) Data Surat** (used for letterhead on both documents)
- Alamat
- Telepon
- Email/Pos-el
(Nama Dinas likely already exists elsewhere in OPD data — reuse it.)

**Logo note:** the existing Blade template already renders the Pemkot Madiun
logo image in the letterhead. This logo is **the same for all OPDs** (it's
the city government's logo, not a per-dinas logo) — it stays **static and
hardcoded**, it is NOT part of the per-OPD dynamic data above. When
refactoring the letterhead block to pull in dynamic OPD fields (nama dinas,
alamat, telepon, email), make sure the existing logo `<img>` markup is
preserved as-is and still renders in both Surat Penerimaan and Sertifikat —
don't let it get dropped or accidentally made dynamic during the refactor.

**b) Penandatangan** — implemented as a **dropdown**, not a single free-text
field:
- The dropdown lists people previously added for this OPD (e.g. "Kepala
  Dinas — Budi S., NIP xxxxxxxx").
- Include an inline **"+ Tambah orang baru"** option inside the dropdown to
  add a new signer (Nama, Jabatan, NIP) without leaving the card — useful for
  cases like a Plt covering while the Kepala Dinas is on leave.
- This same dropdown (with the same saved list) is reused later wherever a
  document needs a signer selected (see sections 3 and 4).

## 2. "Kelola Surat" — New Sidebar Menu (Template Editor)

Add a new sidebar menu **"Kelola Surat"** where Admin OPD edits the **body
text** of two separate templates: one for Surat Penerimaan, one for
Sertifikat.

**How it works:** a rich-text editor where the admin writes the letter body
normally, but can insert **placeholders** — e.g. `{nama_peserta}`,
`{asal_instansi}`, `{opd}`, `{bidang}`, `{tanggal_mulai}`,
`{tanggal_selesai}` — that get automatically substituted with each peserta's
actual data when the PDF is generated. The admin is free to edit the
surrounding wording, add/remove paragraphs, etc.

**What is NOT editable here:** the letterhead (dinas name, address, phone,
email) and the signature block (name, jabatan, NIP) — those are separate,
structurally fixed elements pulled automatically from the "Kelola OPD" data
(section 1), to keep every generated document consistently formatted.

Provide the agent's implementation with a documented list of available
placeholders per template type, and validate that required placeholders
aren't accidentally deleted (or handle gracefully if they are).

## 3. Surat Penerimaan Flow (on approval)

Current flow: Admin OPD fills Bidang, Pembimbing Lapangan, Penanggung Jawab
→ clicks "Setujui Pengajuan" → email + PDF auto-sent to peserta immediately.

**New flow:**
1. Admin OPD fills Bidang, Pembimbing Lapangan, Penanggung Jawab (unchanged).
2. **New field on the same form**: Penandatangan — dropdown from section 1,
   defaulting to the OPD's primary signer but changeable for this specific
   submission.
3. Clicks "Setujui Pengajuan".
4. **No email is sent yet.**
5. Popup appears: **"Download Surat Penerimaan (nama peserta)"**.
6. If not downloaded immediately, the file remains accessible from:
   Dashboard filter **Perlu Keputusan**, menu **Perlu Keputusan**, menu
   **Menunggu TTE**, and **Kelola Peserta** → detail peserta.
7. File name convention: `Surat Penerimaan (nama peserta)`.
8. Peserta status changes to **Menunggu TTE**.
9. Admin OPD uploads the signed PDF via the **Menunggu TTE** menu — row
   action button labeled **"Unggah"** (distinct from "Putuskan" used in
   Perlu Keputusan, to avoid confusing the two stages), upload-only, no
   re-entry of other fields.
10. **On successful upload, the email + signed PDF is sent to the peserta
    automatically.**

## 4. Sertifikat Flow (on completion)

1. When a peserta's magang period ends, status automatically changes to
   **Perlu Sertifikat** (this replaces the old immediate "Selesai Magang"
   transition — see status-machine note below). No manual admin action
   triggers this transition.
2. New sidebar menu **Perlu Sertifikat** lists these peserta. Content is
   **administrative only** (peserta name, OPD, periode magang, etc.) — no
   scoring, grading, or performance notes.
3. From this menu, admin confirms/selects Penandatangan (same dropdown from
   section 1, defaulting to the OPD's primary signer, editable per
   submission) and generates the draft Sertifikat PDF for download — same
   snapshot behavior as Surat Penerimaan (see design note below).
4. Admin uploads the signed Sertifikat PDF (row action, same menu).
5. **On successful upload, the email + signed Sertifikat is sent to the
   peserta automatically, and status becomes Selesai Magang.**

**Status-machine note (confirm/flag if pre-existing logic depends on this):**
"Selesai Magang" now means "magang period ended AND signed Sertifikat has
been issued" — not just "period ended." If any existing dashboard stat,
report, or automated logic (e.g. releasing the OPD's kuota slot) currently
keys off "Selesai Magang" meaning just "period ended," that logic needs to
be reviewed against this new meaning.

## 5. Signer Snapshot (applies to both documents)

The Penandatangan selected at generation time (name, jabatan, NIP) must be
stored as a **snapshot** on the peserta/document record — not just a live
reference to the OPD's signer list. If the list changes later (e.g. new
Kepala Dinas), previously issued documents must still show who actually
signed at the time.

## Acceptance Criteria
- [ ] Kelola OPD card (dashboard) holds Kuota, Tag Kompetensi, Data Surat,
      and a Penandatangan dropdown with inline "add new person."
- [ ] Pemkot Madiun logo still renders correctly in both Surat Penerimaan
      and Sertifikat letterheads after the dynamic-letterhead refactor
      (logo itself stays static/hardcoded, not per-OPD data).
- [ ] Kelola Surat sidebar menu lets admin edit body text (with placeholders)
      for Surat Penerimaan and Sertifikat templates separately; letterhead
      and signature block are not editable there.
- [ ] Surat Penerimaan & Sertifikat PDFs render dynamic letterhead + signature
      per OPD, using the selected Penandatangan and the edited template body.
- [ ] Signer info per generated document is stored as a snapshot.
- [ ] "Setujui Pengajuan" no longer sends email immediately; popup offers
      download; peserta status becomes Menunggu TTE.
- [ ] Menunggu TTE menu/filter/upload ("Unggah") implemented; uploading
      signed PDF triggers the peserta email automatically.
- [ ] Magang period end automatically sets status to Perlu Sertifikat (not
      directly to Selesai Magang).
- [ ] Perlu Sertifikat menu implemented; uploading signed Sertifikat triggers
      auto-email and sets status to Selesai Magang.
- [ ] Existing logic/reports that assumed "Selesai Magang" meant "period
      ended" reviewed and updated for the new meaning.
- [ ] Tests added/updated for the new statuses and shifted email triggers.

## Out of Scope
- Actual e-signature / digital certificate API integration — this is a
  manual sign-on-paper-then-upload-PDF flow.
- Any scoring/grading system for Sertifikat content.
- Editing letterhead/signature layout inside Kelola Surat (that's driven by
  Kelola OPD data, not the template editor).
